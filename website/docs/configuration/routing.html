Routing

Routing determines which registered agent handles an inbound turn after governance and before agent invocation. It is part of the canonical message path inside Chat Agent Relay, not a separate product surface.

Where routing fits

Once an inbound message has crossed the channel boundary and been canonicalized, CAR evaluates governance on the message path. If the turn is allowed to continue, routing decides which registered agent should receive the invocation. 

message.received
  → policy.decision.made
  → route.decision.made
  → agent.invocation.requested

This keeps route choice explicit and replayable instead of hiding it in channel-specific or agent-specific logic.

Route rule types

The current runtime supports three common rule types.

Rule typeWhat it matchesExample
channelA specific registered channel instance--channel=support-discord
patternA regular expression matched against inbound text--pattern="^/code"
defaultThe fallback when no more specific rule matches--default

Evaluation order

Rules are evaluated from more specific toward more general behavior.

  1. Channel rules are checked first.
  2. Pattern rules are checked if no channel rule matches.
  3. Default rule is used if no earlier rule matches.

If no route matches and no default route is present, the turn does not proceed to agent invocation. In that case, CAR records a blocked outcome on the canonical path.

Register agents before routes

Routing targets registered agents, so register the agent-side destinations first.

car agent add general --endpoint=http://localhost:8080/a2a
car agent add coder --endpoint=http://localhost:8081
car agent add support --endpoint=http://localhost:9000

Add routes

Then create the rules that map inbound turns to those registered agents.

# Route a specific channel to a support agent
car route add --channel=support-discord --agent=support

# Route matching text to a coding agent
car route add --pattern="^/code" --agent=coder

# Route everything else to the default agent
car route add --default --agent=general

Example evaluation

For an inbound turn from channel support-discord with text /code fix the bug:

  1. The runtime checks channel rules first.
  2. support-discord matches the configured channel rule.
  3. The turn is routed to support.
  4. Pattern rules are not consulted because a more specific rule already matched.

For an inbound turn from my-slack with text /code refactor the module:

  1. No channel rule matches.
  2. The pattern rule ^/code matches.
  3. The turn is routed to coder.

For an inbound turn from my-slack with text hello:

  1. No channel rule matches.
  2. No pattern rule matches.
  3. The default rule routes the turn to general.

Manage routes

car route list
car route remove <id>

Use these commands to inspect the current route table and remove rules that are no longer wanted.

HTTP API management

When the server runtime is active, route management can also be exposed through the HTTP API.

# List routes
curl -s http://localhost:3000/api/routes

# Add a route
curl -X POST http://localhost:3000/api/routes \
  -H "Content-Type: application/json" \
  -d '{"type":"default","agent":"general"}'

# Remove a route
curl -X DELETE http://localhost:3000/api/routes/2
Boundary discipline Routing chooses the agent-side destination on the canonical message path. It does not turn CAR into an agent orchestration framework or a broad control-plane product; it remains one governed step in the relay path.
