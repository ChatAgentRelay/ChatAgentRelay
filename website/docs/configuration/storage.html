Storage

Storage in Chat Agent Relay preserves runtime configuration and the append-only event ledger for the canonical relay path. SQLite is the default built-in implementation.

What storage means in CAR

Chat Agent Relay is a relay layer between chat platforms and agent runtimes. To keep that path consistent across restarts, CAR relies on two persistence concerns: one holds the runtime configuration that registers channel adapters, agents, and routing, and one holds the append-only event ledger that makes replay and audit possible.

Neither storage surface is the product headline. Both exist to support the governed canonical message path and operational continuity of the relay.

Two storage concerns

ConcernPurpose
Configuration storageChannels, agents, routes, and settings that wire the relay runtime
Ledger storageReplayable append-only event history for audit and replay

Default runtime storage

The default built-in implementation uses SQLite for both concerns. The database file path is set with CAR_DB_PATH (default: ./car.db). SQLite runs in WAL mode for concurrent read performance. 

# Use the default path
car start

# Or specify a custom path
CAR_DB_PATH=/var/lib/car/config.db car start
Encryption at rest Sensitive config values are encrypted when CAR_ENCRYPTION_KEY is set.

Configuration storage layer

The ConfigStore abstraction persists channels, agents, route rules, and key-value settings the runtime needs to operate the relay. SqliteConfigStore is the default implementation. Method-level API detail belongs in reference documentation; here the important point is that configuration storage is the durable backing for the registered runtime state described on the CLI & Config page.

Ledger storage layer

The LedgerStore abstraction backs the append-only event ledger. Events are written once and are not mutated in place, which preserves a trustworthy history for replay and audit. The default implementation also uses SQLite (same database file or a separate file as configured for your deployment). An in-memory implementation exists for testing.

Implementation customization

Both ConfigStore and LedgerStore are interface-driven. Custom implementations can replace either by implementing the interface and wiring them in during server initialization—for example, a team-standard database such as PostgreSQL or a managed cloud store. That flexibility is secondary to CAR’s role as a relay: the default SQLite path is sufficient for most deployments, and swapping storage does not redefine CAR as a storage or extensibility product.
