A2A Protocol Agent

Connect agents that implement Google’s Agent-to-Agent (A2A) protocol — the richest adapter in CAR with streaming, HITL, session management, and artifact support.

What is A2A?

A2A is an open protocol by Google for agent interoperability. It defines a standard HTTP+JSON interface for sending tasks to agents and receiving structured responses, including streaming updates, artifact delivery, and human-in-the-loop signaling.

Chat Agent Relay’s backend-a2a package is a native AgentAdapter implementation. It speaks A2A directly and maps every protocol feature into CAR’s canonical event model.

Register an A2A agent

Use the car CLI to add an A2A agent:

car agent add my-a2a --type=a2a --endpoint=http://localhost:9000

Then route messages to it:

car route add --default --agent=my-a2a

Integration catalog

CAR only needs one thing from an agent runtime: an A2A-speaking HTTP endpoint. How you get there depends on the framework or tool you start from. The sections below list the common paths.

LangGraph and LangChain

LangGraph is typically the direct integration point: deploy the graph behind an A2A-compatible endpoint and register that URL in CAR. For LangChain, the normal pattern is to put an A2A server or bridge in front of the LangChain application rather than trying to have CAR talk to LangChain directly. In practice, LangChain teams often route through LangGraph deployment infrastructure or a python-a2a-compatible wrapper.

Recommended path Prefer LangGraph -> A2A endpoint -> CAR when you already deploy LangGraph. For plain LangChain, prefer LangChain app -> A2A wrapper -> CAR. This keeps the protocol boundary explicit and avoids coupling CAR to framework-specific APIs.

SDK and workflow bridges

SDK-oriented runtimes are usually libraries, not the boundary CAR should call directly. The recommended pattern is: build the agent with the SDK, deploy it behind an HTTP service that speaks A2A, and point CAR at that A2A service.

RuntimeTypical integration pathWhy this shape exists
OpenAI Agents SDKDeploy the SDK behind an A2A-compatible HTTP wrapper, then register the wrapper URL.The SDK is a build-time/runtime library, not the protocol boundary CAR should couple to.
Anthropic Agent SDKExpose the agent through an A2A bridge or MCP-to-A2A relay.Keeps CAR on the A2A boundary while letting the agent stay inside an Anthropic-oriented tool stack.
LlamaIndexWrap the workflow server in a small A2A-facing service.Lets CAR use the same registration flow as for native A2A frameworks.
Flowise, Dify, n8n, Activepieces, Make, ZapierPlace an A2A wrapper in front of the workflow or webhook surface.These systems usually expose HTTP/webhook execution first, so A2A is the compatibility layer in front.

Coding tools and local-agent bridges

For coding tools, keep the editor or CLI protocol behind a bridge and let CAR talk only to the bridge’s A2A endpoint. This keeps CAR transport-neutral and lets the bridge handle local tool permissions, subprocess lifecycle, and tool-specific session behavior.

ToolTypical pathNotes
Claude CodeExpose the runtime through an A2A bridge or MCP-to-A2A relay, then register that bridge in CAR.This avoids coupling CAR to a local editor protocol while preserving A2A features.
OpenCodeRun an OpenCode-to-A2A bridge and point CAR at the published endpoint.Useful when the coding agent is local-first but you want a network-visible A2A façade.
Gemini CLIPut an A2A-capable wrapper or agent gateway in front of the CLI.CAR only sees the A2A bridge.
GitHub Copilot agentsUse a Copilot-to-A2A bridge or a hosting surface that can expose Copilot agents over A2A.Again, the bridge is the protocol boundary CAR registers.
coder/agentapi and similar gatewaysUse the gateway as the stable A2A façade, with the coding tool behind it.Good when you want one CAR-facing endpoint for several local agent tools.

Agent Card Discovery

On creation, the adapter attempts to fetch /.well-known/agent.json from the A2A endpoint. If found, the Agent Card’s capability declarations (e.g. streaming support) are used to populate describeCapabilities(). If the card is unavailable, all capabilities default to true. The agent’s name from the card is used as the actor.id in canonical events.

Streaming

A2A agents can stream responses via Server-Sent Events using the message/stream JSON-RPC method. The adapter’s stream() async generator yields text_delta, status, input_required, and artifact events as they arrive. This enables real-time typing indicators and progressive message updates in channels that support editing (Slack, Discord).

Human-in-the-loop (HITL)

A2A natively supports HITL workflows. When an agent needs human input, it signals via the protocol and CAR emits an agent.input.requested event. The channel adapter presents this to the user and routes their response back as agent.input.provided.

This enables confirmation prompts, clarification questions, and approval workflows without custom code.

Session management

The A2A adapter uses contextId for session continuity. If a sessionHandle is provided it’s used as the contextId; otherwise a new UUID is generated. The contextId returned by the agent is stored as the session handle for subsequent resume() and resumeStream() calls.

Resume & Resume Stream

Both resume() and resumeStream() are supported. They send message/send and message/stream respectively with the same contextId, allowing the agent to continue from where it left off after an input-required state.

Cancel

The adapter supports cancel(sessionHandle) via the A2A task/cancel JSON-RPC method.

Full example

# Register the agent
car agent add research-bot --type=a2a \
  --endpoint=http://agents.internal:9000

# Add custom auth header
car config set agent.research-bot.headers.Authorization "Bearer sk-..."

# Route all messages to it by default
car route add --default --agent=research-bot

# Start the relay
car start
