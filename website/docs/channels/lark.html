Lark / 飞书

Lark is a channel adapter in Chat Agent Relay. It handles Lark- and Feishu-specific ingress and delivery behavior at the chat-platform boundary, including event subscriptions, token-managed delivery, message editing for streaming-capable paths, and chat-type-specific behavior.

Lark / 飞书 boundary

The Lark adapter receives provider-native events from Lark or 飞书, interprets them according to platform rules, canonicalizes them into CAR events, and translates outbound canonical intent back into Lark-native delivery behavior.

The same architectural boundary applies whether the deployment targets the international Lark platform or the Chinese 飞书 platform.

Prerequisites

Create a Lark or 飞书 application:

  1. Create an app in the appropriate developer console.
  2. Enable bot capabilities for the app.
  3. Add permissions required for your deployment, such as messaging and user-identification scopes.
  4. Subscribe to message events using the platform's event-subscription model.
  5. Publish the app and copy the app ID and app secret.

Registering Lark / 飞书

Register the channel with the car CLI:

car channel add my-lark \
--type=lark \
--app-id=cli_xxx \
--app-secret=yyy
Platform coverage The current adapter covers the Lark / 飞书 provider boundary with one integration shape. The architectural point is the boundary contract, not a separate CAR product surface for each regional variant.

Lark / 飞书-specific behavior

ConcernLark / 飞书 behavior at the boundary
Ingress transportThe adapter receives subscribed platform events and converts them into canonical CAR events
Token-managed deliveryThe adapter obtains and refreshes platform access tokens needed for outbound API calls
Conversation shapeP2P and group chat surfaces influence how conversation continuity and actor context are mapped into the canonical path
Streaming presentationWhen the agent side supports streaming, the adapter can progressively update a message using platform-native edit behavior
Mentions and metadataPlatform-specific mention details, tenant context, and message identifiers can be preserved as structured provider extension data

Chat behavior

The adapter supports the main Lark / 飞书 conversation surfaces that matter at the provider boundary.

  • P2P chats — direct conversations between a user and the bot.
  • Group chats — shared chat surfaces where mentions and group message context matter.
  • Provider extensions — tenant, chat, message, and mention data can remain available without becoming CAR's source of truth.

Provider extensions

Lark / 飞书-specific metadata can be preserved in structured provider extensions, including event identity, chat identity, tenant information, and mention details.

Idempotency

The adapter can use provider event identity to deduplicate repeated deliveries at the boundary.

Boundary discipline The Lark adapter is responsible for Lark / 飞书-specific transport and delivery behavior. Governance, routing, A2A invocation, replay, and auditability remain CAR core responsibilities on the canonical message path.
