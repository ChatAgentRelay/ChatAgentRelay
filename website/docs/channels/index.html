Channels

Channels are the chat-platform boundary in Chat Agent Relay. A channel adapter receives provider-native traffic, verifies and canonicalizes it into CAR events, and translates canonical outbound intent back into provider-native delivery behavior.

Channel-side boundary

CAR keeps chat-platform detail at the edge. The channel adapter is where provider-specific transport, verification rules, event payloads, message identifiers, and delivery APIs are handled.

Inside the relay, CAR operates on canonical events rather than provider-native payloads. That is what keeps governance, routing, agent invocation, delivery orchestration, replay, and audit consistent across integrations.

Where channels fit on the message path

provider-native ingress
  → verification and canonicalization
  → message.received
  → governance
  → route decision
  → agent invocation via A2A
  → message.send.requested
  → provider-native delivery
  → message.sent

The adapter owns the provider boundary. The relay core owns the canonical message path.

What a channel adapter is responsible for

ResponsibilityWhat it means
IngressReceive provider-native events from webhooks, sockets, gateways, or HTTP transport surfaces
VerificationValidate signatures, tokens, or other provider-specific authenticity signals where applicable
CanonicalizationNormalize inbound provider payloads into canonical CAR events
Delivery translationConvert canonical outbound intent into provider-native send or edit behavior
Provider extensionsPreserve provider-native metadata as structured extension data without making it CAR's source of truth

Built-in channels

The current repository includes the following built-in channel adapters.

💬
Slack
Socket Mode ingress, threaded delivery, reactions, slash commands, and message updates for streaming-capable paths.
🎮
Discord
Gateway ingress, REST delivery, slash commands, embeds, and guild-scoped access behavior.
🌐
WebChat
HTTP-based channel surface for browser UIs, local development, internal tools, and testing.
✈️
Telegram
Bot API webhook ingress, command handling, and progressive message editing where streaming is supported.
🐦
Lark / 飞书
Event-subscription-based ingress with token-managed delivery and platform-specific message editing behavior.
🔔
DingTalk / 钉钉
Robot callback ingress with session-based reply behavior and DingTalk-specific delivery constraints.

Common capabilities and variations

Channel adapters share the same boundary role, but individual platforms differ in what they support.

  • Streaming presentation — some platforms can progressively edit a message while output is being generated; others can only send a final message.
  • Commands and interaction patterns — some channels support slash commands or bot commands as distinct input families.
  • Conversation shape — some platforms are thread-centric while others are chat-centric or conversation-centric.
  • Access and verification — each provider has its own verification model, permission surface, and delivery constraints.

Registering a channel

Use the car CLI to register a channel adapter instance. Each channel type has its own provider-specific configuration.

car channel add my-slack --type=slack ...
car channel add my-discord --type=discord ...
car channel add web --type=webchat
car channel add my-telegram --type=telegram ...
car channel add my-lark --type=lark ...
car channel add my-dingtalk --type=dingtalk ...

The individual channel pages document the provider-specific setup and configuration required at that boundary.

Boundary discipline Channel adapters are not the place where CAR becomes an inbox, workspace product, or provider-specific source of truth. They are the provider boundary around a canonical relay path.
