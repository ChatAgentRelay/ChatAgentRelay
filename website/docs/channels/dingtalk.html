DingTalk / 钉钉

DingTalk is a channel adapter in Chat Agent Relay. It handles DingTalk-specific ingress and delivery behavior at the chat-platform boundary, including robot callbacks, session-based reply behavior, signature verification, and conversation-type-specific behavior.

DingTalk / 钉钉 boundary

The DingTalk adapter receives provider-native DingTalk robot callbacks, interprets them according to DingTalk's platform rules, canonicalizes them into CAR events, and translates outbound canonical intent back into DingTalk-native delivery behavior.

Once the callback has crossed that boundary, CAR continues on the same governed message path used for every other channel.

Prerequisites

Set up a DingTalk robot for the conversation surface you want CAR to serve:

  1. Create a robot in the relevant DingTalk environment.
  2. Choose the security model appropriate for the deployment, such as IP allowlists, keyword checks, or signature-based verification.
  3. Configure the callback target so DingTalk can send inbound message events to the CAR deployment.
  4. Retain the webhook URL and related credentials needed for outbound replies and verification.

Registering DingTalk

Register the channel with the car CLI:

car channel add my-dingtalk \
  --type=dingtalk \
  --webhook-url=https://oapi.dingtalk.com/robot/send?access_token=xxx

DingTalk-specific behavior

Chat behavior

The adapter supports DingTalk conversation surfaces that matter at the provider boundary.

  • Private conversations — one-to-one message flows where the bot participates directly.
  • Group conversations — shared chat surfaces where DingTalk-specific conversation metadata remains relevant at the edge.
  • Session-scoped reply behavior — outbound replies can follow the provider's current conversation context instead of relying only on a long-lived global webhook.

Boundary limitations

  • No progressive message editing — DingTalk's current robot delivery model does not provide the same streaming-style message update behavior available on some other channels.
  • Provider rate limits — outbound throughput is constrained by DingTalk platform limits.
  • Input shape constraints — inbound behavior depends on the message and callback formats DingTalk exposes at the robot boundary.

Provider extensions

DingTalk-specific metadata can be preserved in structured provider extensions, including message identity, conversation type, conversation title, sender identity, and session reply webhook information.

Idempotency

The adapter can use DingTalk message identity to deduplicate repeated callback deliveries at the provider boundary.

Boundary discipline The DingTalk adapter is responsible for DingTalk-specific transport and delivery behavior. Governance, routing, A2A invocation, replay, and auditability remain CAR core responsibilities on the canonical message path.
