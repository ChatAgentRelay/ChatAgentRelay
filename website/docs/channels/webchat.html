WebChat

WebChat is the HTTP-based channel adapter in Chat Agent Relay. It provides a simple browser-facing chat boundary for local development, internal tools, automated tests, and custom web interfaces while preserving the same canonical relay path used by other channels.

WebChat boundary

WebChat plays the same architectural role as Slack, Discord, Telegram, or other channel adapters. The difference is that its provider boundary is an HTTP surface controlled by CAR rather than an external chat platform API.

That makes WebChat useful when you want a lightweight chat entry point without first integrating a third-party messaging product.

Where WebChat fits on the message path

HTTP request
→ WebChat canonicalization
→ message.received
→ governance
→ route decision
→ agent invocation via A2A
→ message.send.requested
→ HTTP response or stream
→ message.sent

WebChat still feeds the same canonical relay path. The transport surface is different, but the governed message path remains the same.

Good fit for WebChat

  • Local development — exercise the relay path without setting up an external chat platform.
  • Internal tools — add a browser-based chat surface in front of CAR.
  • Custom web UIs — connect your own frontend directly to a channel boundary you control.
  • Automated tests — drive the relay path through a deterministic HTTP interface.

Transport shape

WebChat exposes HTTP endpoints for synchronous interaction and, where configured, streaming interaction. It also supports resumable flows for human-in-the-loop interaction.

CapabilityHow WebChat surfaces it
Synchronous request/responseHTTP JSON request with a final JSON response
StreamingServer-Sent Events when the configured pipeline supports streaming
Resumable interactionFollow-up HTTP endpoints for continuing a paused session
Session continuityConversation identifiers mapped to server-side session handles

Registering WebChat

Register the WebChat channel with the car CLI.

car channel add web --type=webchat

The CAR server then exposes the WebChat transport surface through its HTTP runtime.

Minimum request shape

WebChat requests carry the same kinds of identifiers needed by the canonical relay path: message identity, actor identity, tenant/workspace scope where relevant, and conversation continuity. 

{
"client_message_id": "msg_001",
"text": "Hello!",
"user_id": "user_1",
"tenant_id": "t1",
"workspace_id": "ws1",
"channel_instance_id": "web_1",
"conversation_id": "conv_123"
}

Commands and resumable interaction

WebChat can expose transport-level commands and resumable flows without changing CAR's core architecture. If the connected agent requests additional human input, WebChat can continue that interaction through follow-up HTTP requests tied to the same session handle.

Those are transport capabilities layered on top of the same canonical path, not a separate product surface.
