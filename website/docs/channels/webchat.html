WebChat

HTTP-based channel with synchronous JSON, optional Server-Sent Events streaming, built-in slash commands, human-in-the-loop resume endpoints, and server-side session tracking. Still the simplest way to talk to CAR: no external app registration, OAuth, or platform tokens.

Overview

WebChat exposes a small HTTP API on the channel server port. You can send a message and receive a full reply in one JSON response (POST /api/chat), or open an SSE stream for token-style updates (POST /api/chat/stream). Built-in commands (/help, /status, /clear) are handled at the transport layer without invoking an agent. When an agent needs input, responses include hitl_pending and a session_handle; clients resume with POST /api/chat/resume or POST /api/chat/resume/stream. Conversations are keyed by conversation_id; the server maps that to an internal session handle and exposes session metadata via GET /api/chat/sessions/:id.

WebChat remains ideal for local development, internal dashboards, custom chat UIs, and automated tests — same full CAR pipeline and ledger as other channels, minimal setup.

Add to CAR

Register the WebChat channel (no third-party tokens required):

car channel add web --type=webchat

With car start, the endpoints below are served on the main CAR HTTP API (default http://localhost:3000). The standalone WebChat transport uses the same paths on whichever port you assign to that server.

Sending messages (sync)

POST /api/chat accepts a JSON body and returns a single JSON object with the agent reply and identifiers.

Request body example:

{
  "client_message_id": "msg_001",
  "text": "Hello!",
  "user_id": "user_1",
  "tenant_id": "t1",
  "workspace_id": "ws1",
  "channel_instance_id": "web_1",
  "conversation_id": "conv_123"
}

Example with curl:

curl -X POST http://localhost:3000/api/chat \
  -H "Content-Type: application/json" \
  -d '{
    "client_message_id": "msg_001",
    "text": "Hello!",
    "user_id": "user_1",
    "tenant_id": "t1",
    "workspace_id": "ws1",
    "channel_instance_id": "web_1",
    "conversation_id": "conv_123"
  }'

Response example:

{
  "ok": true,
  "conversation_id": "conv_123",
  "correlation_id": "corr_456",
  "reply": "Hello! How can I help?",
  "session_handle": "sess_abc"
}

When the agent is waiting for human input, the sync response may include "hitl_pending": true, session_handle, and hitl_prompt instead of a final natural-language reply. Use the resume endpoints below to continue.

Full pipeline Agent-handled messages still flow through the same canonical event chain as Slack and Discord: policy, routing, agent invocation, delivery, and ledger. Slash commands short-circuit before canonicalization so they never hit the agent.

Streaming (SSE)

POST /api/chat/stream returns text/event-stream. Each event is one line of the form data: <JSON> (blank line between events), matching the usual SSE framing.

Example stream (abbreviated):

data: {"type":"status","status":"working"}

data: {"type":"text_delta","content":"Hello"}

data: {"type":"text_delta","content":" World"}

data: {"type":"done","conversation_id":"conv_123","correlation_id":"corr_456","reply":"Hello World","session_handle":"sess_abc"}

Event types:

  • text_delta — incremental assistant text (content).
  • status — progress signal (status, optional message).
  • input_required — HITL pause (prompt, session_handle).
  • done — final summary: conversation_id, correlation_id, full reply, optional session_handle, optional hitl_pending.
  • error — failure (message).

Streaming requires a server configuration that supplies a streaming pipeline. If streaming is not configured, the endpoint responds with an error status and JSON body.

Slash commands

These commands are built into the WebChat transport. They do not invoke the agent or the middleware pipeline.

  • /help — Lists available commands.
  • /status — Reports active session count on the WebChat server.
  • /clear — Clears the session mapping for the current conversation_id when provided.

Send them as the message text on POST /api/chat or POST /api/chat/stream; the response is ordinary JSON (sync) or a short stream ending with done depending on the endpoint.

HITL resume

Human-in-the-loop flow:

  1. Send a normal message with POST /api/chat (or stream with POST /api/chat/stream).
  2. If the agent needs input, the sync response includes "hitl_pending": true and a session_handle (and often hitl_prompt). On SSE, you may see an input_required event and a final done with hitl_pending.
  3. Submit the user’s answer with POST /api/chat/resume and JSON body session_handle plus text.

Resume request example:

curl -X POST http://localhost:3000/api/chat/resume \
  -H "Content-Type: application/json" \
  -d '{
    "session_handle": "sess_abc",
    "text": "Yes, proceed with option B."
  }'

For streaming completion after resume, use POST /api/chat/resume/stream with the same JSON body; the response is SSE with the same event types as /api/chat/stream.

Session management

The server keeps a mapping from conversation_id to the latest session_handle for that conversation. Pass a stable conversation_id on each turn for multi-turn chat; new handles are stored as the pipeline returns them.

Inspect the current mapping:

GET /api/chat/sessions/:id

:id is the URL-encoded conversation_id. A successful response includes conversation_id, session_handle, and last_active (ISO timestamp). Unknown IDs return 404.

Frontend integration

Below: synchronous fetch plus SSE over POST using fetch and a readable stream (same data: line discipline as EventSource; native EventSource only supports GET, so POST streaming uses this pattern).

const base = "http://localhost:3000";
const payload = {
  client_message_id: crypto.randomUUID(),
  text: userInput,
  user_id: "user_1",
  tenant_id: "t1",
  workspace_id: "ws1",
  channel_instance_id: "web_1",
  conversation_id: sessionId,
};

// — Sync —
const syncRes = await fetch(`${base}/api/chat`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(payload),
});
const syncData = await syncRes.json();
if (syncData.hitl_pending && syncData.session_handle) {
  // POST /api/chat/resume with { session_handle, text: "..." }
}
displayMessage(syncData.reply);

// — SSE (POST + stream reader, EventSource-style parsing) —
const streamRes = await fetch(`${base}/api/chat/stream`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(payload),
});
const reader = streamRes.body.getReader();
const decoder = new TextDecoder();
let buffer = "";
while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  const lines = buffer.split("\n");
  buffer = lines.pop() ?? "";
  for (const line of lines) {
    if (line.startsWith("data: ")) {
      const event = JSON.parse(line.slice(6));
      if (event.type === "text_delta") appendToken(event.content);
      if (event.type === "done") finalize(event.reply, event.session_handle);
      if (event.type === "input_required") promptUser(event.prompt, event.session_handle);
      if (event.type === "error") showError(event.message);
    }
  }
}

Configuration

Option Description
corsOrigins Allowed CORS origin(s) for browser clients. Configure via CLI when adding the channel (for example --cors-origins=https://app.example.com). Default is permissive for local dev; restrict in production.
Production CORS Set explicit origins in production so only your frontends can call the WebChat API from the browser.
