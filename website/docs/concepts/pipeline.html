Pipeline

The pipeline is the governed canonical message path inside Chat Agent Relay. It starts after inbound traffic has been canonicalized and continues through governance, routing, A2A invocation, delivery, and append-only recording.

Overview

Channel adapters sit at the provider boundary and canonicalize inbound traffic into message.received. From that point onward, the pipeline operates on canonical events rather than provider-native payloads.

The pipeline exists to preserve one stable relay path regardless of channel or agent implementation details.

Core message-path flow

message.received
  → policy.decision.made
  → route.decision.made
  → agent.invocation.requested
  → agent.response.completed
  → message.send.requested
  → message.sent

If the path is denied, blocked, or fails terminally, CAR records event.blocked instead of silently dropping the outcome.

Pipeline stages

StageResponsibilityCanonical outcome
Inbound entryAccept the canonical message.received event produced by the channel boundarymessage.received
Inbound governanceEvaluate message-path policy before routingpolicy.decision.made or event.blocked
RoutingSelect which registered agent should handle the turnroute.decision.made
Agent invocationPass the turn to the agent-side boundary through A2Aagent.invocation.requested, then agent.response.completed or event.blocked
Outbound governanceEvaluate outbound content before deliverycontinue or event.blocked
DeliveryTranslate canonical outbound intent into provider-native send behaviormessage.send.requested, then message.sent or event.blocked
Ledger appendPreserve replayable, auditable history of the pathappend-only record of all relevant outcomes

Illustrative sequence

channel adapter
  → message.received
  → policy.decision.made
  → route.decision.made
  → agent.invocation.requested
  → agent.response.completed
  → message.send.requested
  → message.sent

The important architectural point is that the pipeline processes canonical events. Provider-specific input handling belongs at the channel boundary, and runtime-specific execution behavior belongs behind the agent-side boundary.

Blocked and failed outcomes

The pipeline preserves blocked and terminal failure paths in auditable form.

  • Inbound deny — policy rejects the message before routing.
  • Invocation failure — the agent-side boundary returns a structured failure.
  • Outbound deny — outbound governance blocks the response before delivery.
  • Delivery exhaustion — delivery behavior fails terminally after retry handling where applicable.

In these cases, CAR records event.blocked so the message path remains explainable from the ledger.

Streaming and resumable interaction

Streaming and resumable interaction are extension capabilities layered onto the same relay path. They do not replace the final canonical completion event.

  • Streaming — if both the agent-side boundary and the channel-side delivery path support it, partial output can be surfaced progressively while still ending in a final agent.response.completed.
  • Resumable interaction / HITL — if an agent requests additional human input, CAR can map that flow into canonical events such as agent.input.requested and agent.input.provided, then resume the interaction.
Extension behavior Streaming, status updates, resumable interaction, cancellation, and artifacts are useful relay extensions, but the core pipeline remains the canonical message path from message.received to either completion or event.blocked.

Current implementation

In the current repository, the main implementation of this flow lives in FirstExecutablePathPipeline. That class is an implementation detail of the current codebase, not the architectural definition of the pipeline itself.

Other implementation details, such as route resolution callbacks, policy functions, and delivery orchestration helpers, exist to realize the same relay-centered message path described above.
