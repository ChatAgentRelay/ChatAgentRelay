Event Model

Every interaction in Chat Agent Relay is captured as an immutable event. Events form causal chains that provide full auditability and replay.

The 7-Event Chain

The happy path for every message produces exactly seven events in sequence:

message.received
  └─▶ policy.decision.made
        └─▶ route.decision.made
              └─▶ agent.invocation.requested
                    └─▶ agent.response.completed
                          └─▶ message.send.requested
                                └─▶ message.sent
Event TypeEmitted ByDescription
message.receivedChannel adapterIncoming message canonicalized from the chat platform
policy.decision.madeMiddlewareGovernance evaluation result (allow or deny)
route.decision.madeMiddlewareWhich agent was selected and why
agent.invocation.requestedPipelineAgent call initiated with input payload
agent.response.completedPipelineAgent returned a response (full text or streamed)
message.send.requestedDeliveryResponse queued for delivery to the chat platform
message.sentDeliveryResponse successfully delivered to the chat platform

Error & Deny Path: event.blocked

When something goes wrong, an event.blocked event is emitted instead of the next event in the chain. This happens in two scenarios:

  • Policy deny — The governance layer rejects the message (e.g., keyword filter, access control). The chain stops after policy.decision.made.
  • Runtime error — The agent fails, times out, or delivery is exhausted after retries. An event.blocked records the failure reason.
message.received
  └─▶ policy.decision.made (deny)
        └─▶ event.blocked          ← chain stops here

message.received
  └─▶ policy.decision.made (allow)
        └─▶ route.decision.made
              └─▶ agent.invocation.requested
                    └─▶ event.blocked        ← agent failure

The event.blocked event includes a reason field explaining what went wrong and a blocked_event_type indicating which event would have come next.

Extended Event Types

Beyond the core 7-event chain, Chat Agent Relay supports additional event types for richer interactions:

Message Lifecycle

Event TypeDescription
message.updatedA previously sent message was edited (e.g., Slack message edit)
message.deletedA message was deleted from the chat platform
reaction.receivedA reaction (emoji) was added to a message
command.receivedA slash command was invoked (e.g., /help in Slack or Discord)

Agent Lifecycle

Event TypeDescription
agent.status.changedAgent reported a status update (e.g., "thinking", "working")
agent.input.requestedAgent needs human input to continue (HITL interrupt)
agent.input.providedHuman provided the requested input; agent resumes
15 event types total The contract harness validates all 15 event types against JSON Schema. The 7-event chain covers the core flow; the remaining 8 cover lifecycle signals, error handling, and human-in-the-loop interactions.

Event Envelope Structure

Every event shares a common envelope with these fields:

{
  "event_id": "evt_a1b2c3d4",
  "event_type": "message.received",
  "timestamp": "2025-03-15T10:30:00.000Z",
  "correlation_id": "corr_x9y8z7",
  "causation_id": null,
  "conversation_id": "C123456",
  "channel": "my-slack",
  "payload": {
    "text": "Hello, agent!",
    "sender_id": "U987654",
    "sender_name": "alice"
  },
  "provider_extensions": {
    "slack": {
      "team_id": "T111",
      "thread_ts": "1710500000.000100"
    }
  }
}
FieldTypeDescription
event_idstringUnique identifier for this event
event_typestringOne of the 15 canonical event types
timestampISO 8601When the event was created
correlation_idstringShared across all events in a single request chain
causation_idstring | nullThe event_id of the event that caused this one
conversation_idstringGroups events into a conversation thread
channelstringName of the channel adapter that produced or will consume this event
payloadobjectEvent-type-specific data
provider_extensionsobjectPlatform-specific data preserved from the original message

Causal Chain

The correlation_id and causation_id fields together form a causal chain. All events triggered by a single incoming message share the same correlation_id. Each event's causation_id points to the event that directly caused it: 

message.received (evt_001, causation: null)
  └─▶ policy.decision.made (evt_002, causation: evt_001)
        └─▶ route.decision.made (evt_003, causation: evt_002)
              └─▶ agent.invocation.requested (evt_004, causation: evt_003)
                    └─▶ agent.response.completed (evt_005, causation: evt_004)
                          └─▶ message.send.requested (evt_006, causation: evt_005)
                                └─▶ message.sent (evt_007, causation: evt_006)

All share correlation_id = "corr_x9y8z7"

This allows you to query any event and trace the full chain forwards or backwards. The audit API uses these links to build human-readable explanations of what happened and why.
