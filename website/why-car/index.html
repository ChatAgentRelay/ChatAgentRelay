Why Chat Agent Relay Exists

Open-source relay layer · canonical events, governance, routing, delivery reliability, and auditability

The problem

Teams repeatedly rebuild the same chat-to-agent integration path:

  • verify and canonicalize inbound platform traffic
  • apply message-path governance before an agent sees the turn
  • route the turn to the right agent
  • invoke the agent and map its result back into a stable form
  • deliver the response reliably and preserve what happened for audit

That work is necessary, but it is usually not the core product the team is trying to build.

The idea

Chat Agent Relay makes that layer explicit. CAR is a standard relay layer between chat platforms and agents, centered on canonical events and the governed message path.

Instead of letting every provider payload shape and every agent integration detail leak into application code, CAR keeps channel-specific and agent-specific behavior at the boundaries and keeps the message path inside the relay consistent.

The message path

message-path.txt 
message.received
  → policy.decision.made
  → route.decision.made
  → agent.invocation.requested
  → agent.response.completed
  → message.send.requested
  → message.sent

blocked or terminal failure path:
  → event.blocked

This canonical path gives CAR one stable internal contract for governance, routing, delivery, replay, and audit across multiple chat platforms and agent integrations.

Boundary model

Channel-side boundary

Channel adapters receive provider-native traffic, verify it where applicable, canonicalize it into CAR events, and translate outbound canonical intent back into provider-native delivery behavior.

CAR core

CAR owns canonical event semantics, message-path governance, route decisions, delivery orchestration, and append-only replay/audit truth.

Agent-side boundary

CAR uses A2A as the standard agent-side protocol boundary. The remote runtime keeps ownership of its internal execution model, private memory, tools, and framework-specific state.

Why that matters

Canonical events first

The message path is replayable and explainable because the relay runs on canonical events instead of raw provider payloads.

Governed message path

Policy runs before routing and before delivery, so blocked outcomes remain part of the same auditable path.

A2A at the agent boundary

The relay stays focused on the boundary to agents instead of turning into a general-purpose runtime abstraction layer.

Replay and audit

An append-only ledger preserves what happened on the message path and why, without depending on scattered logs or runtime-private state.

Extensible boundaries

Channel adapters and agent adapters can be extended while preserving the same relay-centered architecture.

What Chat Agent Relay is not

  • Not an agent runtime or orchestration framework
  • Not an agent-internal governance platform
  • Not an inbox, CRM, or SaaS workspace product
  • Not the place where runtime-private execution state becomes CAR's source of truth

Current repository shape

  • Built-in channel adapters for major chat platforms
  • Built-in A2A agent adapter
  • Canonical event contracts and schema validation
  • Middleware for governance and routing
  • Delivery orchestration and retry behavior
  • Append-only ledger for replay and audit
  • Conformance tooling for adapter validation
