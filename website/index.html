open source · MIT license · TypeScript

A standard relay layer
between chat platforms and agents.

You built an agent. Now teams want it in Slack, Teams, Discord, or web chat. Compliance asks what happened to a message. Product wants routing, retry, and governance to behave consistently.

Chat Agent Relay provides that message path once. CAR canonicalizes inbound chat traffic, governs and routes it, invokes agents through A2A, delivers responses, and preserves replayable audit history in an append-only ledger.

Get Started View on GitHub
terminal 
$ git clone https://github.com/ChatAgentRelay/ChatAgentRelay && cd ChatAgentRelay
$ bun install
installed workspace packages
$ cd packages/server && export CAR_ENCRYPTION_KEY=$(openssl rand -hex 32)
$ car channel add slack --type=slack --bot-token=xoxb-... --app-token=xapp-...
$ car agent add bot --type=a2a --endpoint=http://localhost:9000
$ car route add --default --agent=bot
$ car start
[car] Channel registered · Agent registered · Relay running
The Problem

Chat-to-agent plumbing keeps getting rebuilt

Teams repeatedly rebuild webhook verification, canonicalization, routing glue, retry behavior, and audit trails for each new chat surface or agent integration. That work is necessary, but it is rarely the product.

Architecture

Canonical events at the center of the relay path

CAR keeps channel-specific and agent-specific behavior at the boundaries. Inside the relay, middleware operates on canonical events so governance, routing, delivery, replay, and audit stay consistent.

architecture 
Chat Platforms        Chat Agent Relay                      Agents
┌──────────────┐     ┌──────────────────────────────────┐   ┌───────────────┐
│ Slack        │     │ Channel Adapters                 │   │ Remote Agent  │
│ Teams        │────>│ Canonical Events                 │──>│ via A2A       │
│ Discord      │     │ Governance + Routing             │   │               │
│ Telegram     │     │ Delivery + Retry                 │   │               │
│ Web Chat     │     │ Append-Only Ledger / Audit       │   │               │
└──────────────┘     └──────────────────────────────────┘   └───────────────┘
1 → message.received  inbound message canonicalized from the chat platform
2 → policy.decision.made  message-path governance result
3 → route.decision.made  route selection for the turn
4 → agent.invocation.requested  canonical invocation handed to the agent-side boundary
5 → agent.response.completed  agent result mapped back into canonical form
6 → message.send.requested  outbound intent prepared for delivery
7 → message.sent  delivery outcome recorded
× → event.blocked  blocked or terminal failure path kept auditable
What CAR Provides

A governed, replayable chat-to-agent message path

events

Canonical Event Model

Provider-native input becomes canonical events, giving the relay one stable internal contract across channels and agents.

gov

Message-Path Governance

Inbound and outbound governance run on canonical events before routing and before delivery.

route

Routing

Route rules choose which registered agent handles a turn without changing channel integrations.

a2a

A2A Agent Boundary

CAR uses A2A as the standard agent-side protocol boundary while keeping runtime-private state on the agent side.

retry

Delivery Reliability

Outbound delivery behavior includes retry handling and structured blocked outcomes instead of silent failure.

audit

Replay and Audit

An append-only ledger preserves what happened on the message path and why.

Boundaries

Narrow boundaries on both sides of the relay

Channel adapters

Receive provider-native traffic, verify it where applicable, canonicalize it, and translate canonical outbound intent back into provider-native delivery actions.

CAR core

Owns canonical events, governance, routing, delivery orchestration, replay, and auditability on the message path.

Remote agents

Keep ownership of their internal execution model, private memory, tools, and framework-specific runtime state.

CAR vs rebuilding the relay yourself
